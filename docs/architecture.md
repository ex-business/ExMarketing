# ExMarketing Architecture

## Goal

`ExMarketing` is a standalone marketing platform that can connect to any business system through events, fact queries and reward commands.

## Core Modules

```text
Event Intake
  -> Idempotency
  -> Campaign Match
  -> Rule Evaluation
  -> Quota / Budget / Inventory
  -> Grant Order
  -> Outbox
  -> External Reward System
```

## First Milestone

```text
marketing_activity

marketing_reward
marketing_event_inbox
marketing_participation

```

## API Boundary

External business systems should only integrate through:

```text
Event In        report user/business events
Fact Query      optional external facts
Command Out     reward commands generated by ExMarketing
Callback In     reward delivery result
```

## Current Implementation

The first version is a single Go service with internal module boundaries that mirror the future service split:

```text
internal/httpapi      admin and openapi HTTP boundary
internal/engine       activity match -> rule evaluation -> reward calculation -> grant order -> outbox
internal/marketing    core domain model and repository interface
internal/rule         four-stage rule engine and evaluator registry
internal/reward       fixed and ratio reward calculators
internal/decimal      exact decimal arithmetic for money
internal/worker       outbox sender with retry and DLQ
internal/fact         HTTP fact provider client
internal/plugin       activity plugin registry contract
```

ActivityPlugin is an optional extension point for new gameplay contexts such
as lottery, red-packet rain, sign-in, task, VIP, or invite mechanics. A plugin
may build deterministic context exposed only as `state.plugin.<pluginCode>.*`,
return a precheck result, and preview post-qualification stateChangeIntents.
It must not replace rule evaluation, reward calculation, quota reservation,
participation, grant_order, outbox, callback, or idempotency handling. This
phase does not add plugin state tables or execute real gameplay state changes.

The service supports two repository modes:

```text
default                         in-memory repository
EX_MARKETING_DATABASE_URL set    PostgreSQL repository
```

Local PostgreSQL is provided by `docker-compose.yml`. Schema initialization and
upgrades are applied through `go run ./cmd/db-migration-release --mode apply`,
which records successful versions in `schema_migrations` and blocks checksum
or schema drift.

`db/migration/001_marketing_core.sql` creates the core activity, rule, reward,
quota, event inbox, participation, grant order, outbox and manual export tables.
`db/migration/002_audit_fact_outbox_indexes.sql` adds audit records, fact
provider metadata and indexes for quota/outbox processing.

## Implemented Next-Step Capabilities

```text
Quota reservation:
  marketing_quota supports BUDGET, STOCK, USER_LIMIT and DAILY_LIMIT reservations.
  For rewardable events, participation creation, quota reservation, grant_order
  creation and outbox creation are committed in one activity-level transaction.
  PostgreSQL uses conditional UPDATE statements to avoid read-after-write races.
  STOCK uses ACTIVITY scope with rewardCode as scopeKey; missing quota rows mean
  unlimited quota for backward compatibility.
  SUCCESS callbacks confirm frozen reservations into used quota. FAILED callbacks
  and the Admin timeout-release operation release frozen quota. USER_LIMIT and
  DAILY_LIMIT are participation-level reservations and finalize once per
  participation based on the aggregate grant result.

Outbox sender:
  EX_MARKETING_OUTBOX_WORKER=true enables HTTP/WEBHOOK/MQ delivery.
  EX_MARKETING_MQ_SENDERS_JSON provides runtime-only provider endpoints,
  authRef, TLS file references, send timeout, and destination allowlists.
  MQ delivery is behind a sender adapter boundary for Kafka ack, RabbitMQ
  publisher confirm, and Pulsar send ack. SENT means the command reached the
  broker, not that the reward succeeded. Failed messages retry with backoff and
  then move to DLQ.

Simulation:
  POST /admin/v1/simulate evaluates matching activities without writing inbox,
  participation, grant_order, quota, or outbox rows.

Rule execution:
  Rules run in the fixed business order MATCH -> QUALIFY -> REWARD ->
  RISK_LIMIT_BUDGET. The last business stage groups stored RISK and LIMIT
  rule phases; BUDGET remains a quota type, not a rule_phase.
  Each rule returns status, passed, reasonCode, reason, field, expected,
  actual and sort details. Disabled rules are reported as SKIPPED and do not
  affect the decision. New rule types are added by registering an evaluator in
  internal/rule.Registry; the engine service only invokes the staged rule
  executor.

Fact query:
  POST /openapi/v1/facts/query queries an enabled registry provider by tenantId
  and factCode, maps provider JSON into facts.<factCode>.*, and caches only
  successful mapped facts by provider configuration version plus normalized
  standard event context. Event attributes remain the preferred source when
  rules do not reference facts.*.

Audit:
  activity creation, quota creation, event intake and quota rejection are recorded
  in marketing_audit.

Admin page:
  GET /admin/ serves a minimal local admin page for activity list/create and simulation.
```
