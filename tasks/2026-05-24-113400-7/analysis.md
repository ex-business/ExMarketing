## 背景目标

ExMarketing 是独立活动营销中台，活动上线前必须在后台侧完成可解释、可审核、可阻断的配置校验，避免错误配置直接进入 `SCHEDULED` 或 `ACTIVE` 后造成超预算、超库存、重复命中、互斥冲突、错误发奖或高危资金风险。

本需求目标是定义“上线前配置校验与审批”的业务能力：

- 后台能对待上线活动返回逐项校验结果。
- 高危或校验失败的配置不能直接上线。
- 需要二级审批的配置必须进入审批流程，审批通过前不得上线。
- 校验结果需要可解释，能用于后台展示、审计和后续自动化测试。

## 参与方

- 活动运营：创建、修改活动配置，发起上线校验和上线申请。
- 审批人 / 二级审批人：审核高危或需复核的活动配置。
- 后台管理系统：承载活动配置、校验结果、审批状态展示和操作入口。
- ExMarketing 服务：负责活动配置校验、审批状态约束、审计记录和上线阻断。
- 外部发奖系统：不参与审批，只接收上线后活动产生的发奖指令。

## 输入

校验对象为单个活动的完整配置快照，至少包含：

- 活动基础字段：`tenantId`、`activityCode`、`activityName`、`activityType`、`status`、`triggerEvents`、`startTime`、`endTime`、`timezone`、`priority`、`exclusiveGroup`、`stackable`、`version`。
- 规则配置：`rules[].ruleCode`、`rulePhase`、`ruleType`、`ruleConfig`、`sort`、`enabled`、`version`。
- 奖励配置：`rewards[].rewardCode`、`rewardType`、`calculateType`、`rewardConfig`、`grantMode`、`grantChannel`、`enabled`、`version`。
- Quota 配置：活动预算 `BUDGET`、奖品库存 `STOCK`、用户次数 `USER_LIMIT`、每日次数 `DAILY_LIMIT` 中已配置项。
- 操作上下文：操作者、发起原因、目标动作，目标动作包括创建草稿校验、提交审批、审批通过、上线。

## 输出

后台必须获得结构化校验结果，包含：

- 总体结论：`PASS`、`WARN`、`BLOCK`、`APPROVAL_REQUIRED`。
- 是否允许上线：布尔值。
- 是否需要二级审批：布尔值。
- 校验项列表：每项包含校验编码、名称、等级、结果、原因、涉及字段、当前值、期望值、建议处理方式。
- 高危配置列表：说明触发的高危原因和是否必须审批。
- 审批状态：未提交、待审批、审批通过、审批拒绝、已撤回等。
- 审计信息：操作者、操作时间、活动 ID、活动版本、配置摘要、校验结果摘要、审批意见。

## 业务规则

### 1. 校验触发时机

- 创建或更新活动配置时，应执行基础配置校验并返回结果。
- 活动从 `DRAFT` 或可编辑状态申请进入 `SCHEDULED` / `ACTIVE` 前，必须执行完整上线前校验。
- 审批通过后，如果活动配置再次变更，原审批结果失效，必须重新校验和重新审批。
- 直接创建 `ACTIVE` 活动也必须先通过完整校验；不能因为请求中带 `status=ACTIVE` 而跳过。

### 2. 校验等级

- `ERROR`：阻断上线，必须修复。
- `HIGH_RISK`：不一定代表配置非法，但必须二级审批；未审批通过前阻断上线。
- `WARN`：允许上线，但必须返回提示并写入审计。
- `INFO`：仅用于解释。

总体结论规则：

- 任一 `ERROR` 存在，总体为 `BLOCK`，不允许提交上线。
- 无 `ERROR` 但存在需审批的 `HIGH_RISK`，总体为 `APPROVAL_REQUIRED`，审批通过前不允许上线。
- 仅存在 `WARN`，总体为 `WARN`，允许上线。
- 全部通过，总体为 `PASS`，允许上线。

### 3. 概率总和校验

- `PROBABILITY` 奖励必须校验 `items` 配置合法。
- 概率项权重必须为可解析 Decimal 或整数，且不能为负数。
- 至少存在一个有效概率项。
- 如果业务配置使用百分比表达，则总和必须等于 100%；如果使用权重表达，则权重总和必须大于 0。
- 空奖项如被支持，应作为一个明确奖项参与概率校验，不能通过缺省概率隐式表达。
- 概率校验失败为 `ERROR`，阻断上线。

### 4. 奖励金额超预算校验

- 金额计算必须按 Decimal 语义评估，不能使用浮点近似。
- `FIXED`、`RATIO`、`LADDER`、`RANDOM`、`PROBABILITY`、`POOL_SPLIT` 均需评估单次最大奖励暴露。
- 已配置活动总预算 `BUDGET + ACTIVITY + TOTAL` 时，奖励最大暴露不能确定或明显超过预算，应返回 `ERROR` 或 `HIGH_RISK`。
- 未配置预算但存在现金、礼金、可执行 HTTP/WEBHOOK 自动发奖时，应标记为 `HIGH_RISK`，需要二级审批。
- 多奖励活动应按同一次参与可能产生的奖励合计评估预算影响。

### 5. 库存校验

- 每个 enabled reward 如需要库存，应检查是否存在 `STOCK + ACTIVITY + rewardCode` quota。
- 库存值必须可解析、非负，且与奖励配置的预期发放方式匹配。
- 概率奖、实物奖、奖池类活动如没有库存或库存为 0，应返回 `ERROR` 或 `HIGH_RISK`。
- 缺少库存 quota 对普通无限量活动可作为 `WARN`，但对明确库存型活动必须阻断。

### 6. 活动时间冲突校验

- `startTime`、`endTime`、`timezone` 必填且合法。
- `startTime` 必须早于 `endTime`。
- 同一 tenant 下，活动时间窗口与已存在可上线/在线活动重叠时，需要结合 `triggerEvents`、`activityType`、`exclusiveGroup`、`stackable` 判断冲突。
- 同一互斥组且时间重叠、触发事件重叠、`stackable=false` 的活动，应返回冲突结果。
- 时间冲突如果会导致同一用户同一事件命中多个不可叠加活动，应为 `ERROR`。

### 7. 互斥组冲突校验

- `exclusiveGroup` 相同的活动默认只允许命中一个。
- 同组活动如果时间、租户、触发事件存在交集，且优先级无法明确决定唯一命中，应阻断。
- 同组活动如果允许叠加，必须显式配置 `stackable=true`，否则按不可叠加处理。
- 优先级相同且存在冲突时，应返回 `ERROR`。

### 8. 规则字段校验

- `CONDITION` 字段路径只能使用当前数据模型允许的前缀：`attributes.*`、`state.*`、`facts.*`。
- 字段路径为空、操作符非法、值类型与操作符不匹配，返回 `ERROR`。
- 未注册或当前不支持的 `ruleType` 不得静默通过。
- `rulePhase` 只能使用数据模型定义的 `MATCH`、`QUALIFY`、`REWARD`、`RISK`、`LIMIT`；`BUDGET` 不是合法 `rulePhase`。

### 9. JSON Schema 校验

- 活动、规则、奖励、quota、审批请求均需拒绝未知顶层字段。
- `rewardConfig` 和 `ruleConfig` 必须按 `calculateType` / `ruleType` 做结构校验。
- Decimal 字段、URL 字段、版本字段、枚举字段必须返回机器可识别错误。
- `AUTO + HTTP/WEBHOOK` 发奖必须配置 http(s) `targetRef`。
- 当前不支持的 `MQ`、`MANUAL_EXPORT`、`MANUAL`、未知 calculateType 或未知 grantChannel 必须阻断。

### 10. 高危配置识别

以下情况应标记为 `HIGH_RISK`，至少需要二级审批：

- 自动发放现金、礼金或其他资金类奖励。
- 未配置总预算但存在可执行自动发奖。
- 单用户或单次奖励金额超过后台配置阈值。
- 活动总预算超过后台配置阈值。
- 概率奖、随机金额、奖池瓜分等结果不完全固定的奖励。
- 修改已上线或已审批活动的奖励、预算、库存、互斥组、时间窗口。
- 放宽用户次数、IP/Device 限制或移除关键风控规则。
- 发奖目标 `targetRef` 变更。

阈值本需求不固定具体数值，必须作为后续配置或产品确认项。

### 11. 二级审批

- 触发 `HIGH_RISK` 的上线申请必须进入待审批状态。
- 审批人不能与提交人相同。
- 审批必须记录审批人、审批意见、审批时间、活动版本和校验结果摘要。
- 审批拒绝后活动不得上线，需修改配置后重新提交。
- 审批通过只对当前活动版本有效。
- 存在 `ERROR` 时不能进入审批通过状态；必须先修复配置。

### 12. 上线阻断

- 未完成完整校验的活动不得进入 `SCHEDULED` 或 `ACTIVE`。
- 校验结果为 `BLOCK` 的活动不得上线。
- 校验结果为 `APPROVAL_REQUIRED` 且审批未通过的活动不得上线。
- 阻断结果必须返回逐项原因，不能只返回通用失败。

## 边界条件

- 多租户隔离：冲突、预算、库存、审批和审计均限定在同一 `tenantId` 内。
- 时间边界：相邻但不重叠的时间窗口不应误判冲突；跨时区必须按明确 `timezone` 解释。
- 草稿活动：允许保存存在 `WARN` 或部分业务不完整的草稿，但提交上线必须完整校验。
- 已上线活动：修改关键配置应视为新版本，需要重新校验和审批。
- 缺少 quota：现有运行语义允许缺少 quota 表示不限制；上线校验需按活动类型和奖励风险给出 `WARN` 或 `HIGH_RISK`，不能简单等同合法。
- 结果为 0 的奖励：仍需校验配置合法性，但预算/库存影响可为 0。

## 异常场景

- 活动不存在或 tenant 不匹配：返回不可校验。
- 配置 JSON 解析失败：返回 `ERROR` 并定位字段。
- Decimal 解析失败：返回 `ERROR`。
- 当前配置版本与审批版本不一致：审批失效，要求重新提交。
- 审批人等于提交人：拒绝审批操作。
- 审批通过后上线前发现活动配置已变化：阻断上线。
- 依赖的已有活动列表读取失败：不能给出可靠冲突判断，应阻断上线或返回校验不可完成。

## 非目标范围

- 不实现具体前端页面交互设计。
- 不定义具体代码结构、包拆分或数据库迁移方案。
- 不接入外部 OA / IM 审批系统。
- 不改变事件接入、发奖回调、Outbox 投递和 Fact Query 的既有业务语义。
- 不负责真实钱包加钱、用户注册、订单支付、风控判定等外部业务能力。
- 不在本需求中固定高危阈值的具体金额，阈值需产品或运营确认。

## 风险

- 高危阈值未明确会影响审批触发的一致性。
- 预算暴露评估对 `RATIO`、`RANDOM`、`PROBABILITY`、`POOL_SPLIT` 依赖配置上限；缺少上限时只能标记高危或阻断。
- 互斥冲突需要读取同 tenant 下其他活动，若数据源不完整会误判。
- 审批状态如果不绑定活动版本，会出现“审批旧配置、上线新配置”的风险。
- 缺少后台鉴权设计时，审批接口不能作为生产无鉴权管理操作暴露。

## 验收标准

1. 对一份合法低风险活动配置执行上线前校验，返回总体 `PASS`，逐项校验结果均可展示，允许进入 `SCHEDULED` 或 `ACTIVE`。
2. 概率奖配置概率非法时，返回 `BLOCK`，校验项明确指出概率总和或权重问题，并阻止上线。
3. 奖励最大暴露超过已配置预算时，返回 `BLOCK` 或明确的高危阻断结果，并说明预算差额或无法覆盖的原因。
4. 库存型奖励缺少或库存不足时，返回逐项库存校验失败，并阻止上线。
5. 同 tenant、同互斥组、时间窗口和触发事件重叠且不可叠加的活动，提交上线时返回互斥冲突。
6. `rulePhase=BUDGET`、未知 `ruleType`、未知字段路径、非法操作符、非法 Decimal、非法 URL 均返回机器可识别校验错误。
7. 自动发奖资金类、高预算、随机/概率/奖池类等高危配置返回 `APPROVAL_REQUIRED`，审批通过前不能上线。
8. 二级审批通过后，同一活动版本允许上线；配置变更后原审批失效。
9. 审批拒绝后活动不能上线，校验/审批结果可被后台读取并展示。
10. 所有提交校验、审批通过、审批拒绝、上线阻断动作写入审计，包含操作者、活动版本和原因摘要。
11. 返回结果必须包含逐项校验结果，不能只返回单一错误字符串。

## 待确认问题

- 高危阈值具体数值：单次奖励金额阈值、活动总预算阈值、随机/概率活动是否全部强制二审。
- 审批角色来源：当前是否只要求传入操作者字符串，还是需要接入真实后台账号和权限体系。
- 审批状态枚举是否需要持久化到活动表，还是独立审批记录。
- `POOL_SPLIT` 的预算暴露是否要求必须配置奖池总额，缺失时是 `ERROR` 还是 `HIGH_RISK`。
- 实物奖品是否已纳入当前 `rewardType` 范围；如未纳入，本需求只按现有 `BONUS/CASH/POINT` 和库存型奖励处理。
