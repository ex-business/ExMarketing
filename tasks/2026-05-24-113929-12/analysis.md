## 背景目标

ExMarketing 的定位是独立活动营销中台，目标是用统一活动定义、统一规则、统一奖励、统一预算库存、统一发奖和统一审计承载多种营销活动。当前任务要求补齐管理后台通用配置页面，来源于“22-独立活动营销中台设计”中“后台不应再为每个活动单独堆一套页面，应拆成通用配置组件”的要求。

本需求的目标不是新增某个具体活动页面，而是让运营可以通过统一后台配置普通活动，并完成上线前校验、模拟运行、审批和审计查看。验收结果应体现：新增或调整首存、续存、签到、任务、VIP、邀请、抽奖/红包等可配置活动时，优先通过通用配置组件完成，不再为每个活动单独堆页面。

## 参与方

- 运营人员：创建、编辑、复制、暂停、查看活动配置；配置展示入口、规则、奖励、预算库存、互斥、风控条件和发奖方式。
- 审批人员：审核活动配置版本，处理一级/二级审批，通过或驳回上线申请。
- 测试/产品人员：通过模拟运行输入标准事件样例，验证命中、拒绝、奖励和 quota 影响。
- 技术/运维人员：查看审计、模拟结果、发奖通道配置、DLQ/对账入口的关联信息，用于排障。
- 外部业务系统：不直接使用后台页面，但页面配置结果会影响标准事件处理、Reward Command 输出和回调对账。

## 输入输出

### 页面输入

- 活动基础信息：`tenantId`、`activityCode`、`activityName`、`activityType`、`status`、`triggerEvents`、`startTime`、`endTime`、`timezone`、`priority`、`pluginCode`、`exclusiveGroup`、`stackable`。
- 展示与入口配置：`config.display`、`config.entry`、`config.audience`、`config.metadata`，其中入口、渠道、来源系统、租户、人群等必须遵循现有 `config_json` 一层字段白名单。
- 规则配置：`ruleCode`、`rulePhase`、`ruleType`、`ruleConfig`、`sort`、`enabled`。
- 奖励配置：`rewardCode`、`rewardType`、`calculateType`、`rewardConfig`、`grantMode`、`grantChannel`、`enabled`、`version`。
- Quota 配置：`activityId`、`quotaType`、`scope`、`scopeKey`、`totalValue`。
- 审批输入：`operator`、`expectedVersion`、`reason`。
- 模拟运行输入：标准事件模型，包含 `eventId`、`eventType`、`sourceSystem`、`tenantId`、`subject`、`biz`、`occurredAt`、`attributes`。

### 页面输出

- 活动列表和详情，能展示基础信息、配置版本、状态、审批状态、更新时间和关键配置摘要。
- 配置表单的保存结果和字段级错误提示，错误需映射到可理解的业务字段，而不是只展示通用失败。
- 上线前校验结果，至少覆盖 Schema、时间、规则字段、奖励配置、预算库存、互斥叠加、高危配置和审批要求。
- 模拟运行结果，展示命中活动、未命中原因、规则阶段结果、奖励预览、quota 影响、participation 预览、grant order/outbox 预览。
- 审批记录和操作审计摘要，能看到操作人、动作、资源、版本、原因和时间。

## 业务规则

1. 后台必须围绕通用活动模型配置，不得为单个活动类型固化独立页面模型。
2. 活动创建和更新必须遵循 `tenantId + activityCode` 同租户唯一；不同租户允许复用 `activityCode`。
3. 活动时间必须使用带时区偏移的 RFC3339 时间，且 `startTime < endTime`；`timezone` 必须显式填写并可识别。
4. 只有审批通过且版本一致的活动，才允许进入 `SCHEDULED` / `ACTIVE`；正式事件处理只匹配 `status=ACTIVE` 的活动。
5. 活动扩展配置只允许通用字段：`entry`、`display`、`audience`、`metadata`；未知一层字段应提示并拒绝保存。
6. 入口配置只影响候选活动匹配，不替代活动状态、时间、审批或规则判断。`display.visible=false` 只影响展示可见性，不应让模拟运行或内部事件处理失效。
7. 规则阶段只允许 `MATCH`、`QUALIFY`、`REWARD`、`RISK`、`LIMIT`；`BUDGET` 是 quota 类型，不是合法规则阶段。
8. 当前最小可验收口径下，页面允许配置并校验 `CONDITION` 规则；`FORMULA`、`LIMIT`、`SCRIPT` 如无已注册 evaluator，应展示为暂不可用或保存时拒绝，不能伪装为可运行能力。
9. 规则字段路径只能来自标准事件字段、`attributes.*`、`facts.<factCode>.*`、`state.activity.*`、`state.subject.*`、`state.quota.*`、`state.exclusive.*`、绑定插件时的 `state.plugin.<pluginCode>.*`。
10. 奖励类型允许 `BONUS`、`CASH`、`COUPON`、`POINT`、`GIFT`、`DRAW_CHANCE`、`MEMBERSHIP`；金额类必须使用 Decimal 语义并配置必要币种。
11. 当前可执行发奖模式最小口径为 `grantMode=AUTO`，`grantChannel=HTTP/WEBHOOK/MQ`，且 `targetRef` 必填并符合通道格式。`MANUAL` / `MANUAL_EXPORT` 不纳入本需求上线范围。
12. Quota 配置覆盖 `BUDGET`、`STOCK`、`USER_LIMIT`、`DAILY_LIMIT`，scope 最小支持 `ACTIVITY`、`USER`、`IP`、`DEVICE`；缺少 quota 行表示不限额，但页面必须明确展示“不限额”。
13. 互斥叠加通过 `exclusiveGroup` 和 `stackable` 配置表达，同组默认只命中一个；高优先级活动优先。
14. 风控配置在本需求中默认通过规则条件表达，例如风险标签、IP、设备、渠道、人群等；不要求后台内置真实风控判定或连接风控系统。
15. 模拟运行必须无业务副作用，不写入正式 inbox、participation、grant_order、outbox 或 quota 消耗；如写审计，必须脱敏。
16. 所有配置修改、审批、模拟运行、quota 创建等关键操作必须可追踪到审计记录。

## 边界条件

- 空活动列表时，页面应提供创建入口，并说明当前没有活动，而不是展示错误。
- 新建活动默认为草稿口径；未审批版本不得直接上线为 `ACTIVE`。
- 编辑已审批活动时，配置版本变化会使旧审批失效，页面必须提示需要重新提交审批。
- `entry.tenantIds` 只能为空或包含活动自身 `tenantId`，不得扩大租户边界。
- `entry.channels`、`entry.sourceSystems`、`audience` 条件为空时表示不限制；非空时按标准事件字段匹配。
- 规则中引用 `facts.*` 时，必须依赖已启用的 Fact Provider；未配置 provider 时应阻止上线或在校验中明确失败。
- 奖励计算结果为 0 且无实际权益时，应在模拟结果中解释为不生成发奖单、不扣 quota。
- 非金额权益即使 `reward_amount=0.0000`，只要权益数量有效，也应在预览中展示 grant order/outbox 影响。
- 高危活动默认口径：涉及高金额预算、概率/随机奖励、资金类奖励、复杂插件或生产发奖通道时需要二级审批；具体阈值若现有材料未定义，最小可验收口径为页面必须展示“是否高危/是否二级审批”的判定结果和原因。
- 后台当前只面向本地开发或受保护管理环境；未设计鉴权前，不得把新增管理能力作为公网生产无鉴权页面交付。

## 异常场景

- 保存活动时字段类型、时间、状态流转、未知 JSON 字段、重复 `activityCode`、非法 `pluginCode`、非法规则字段、非法奖励组合或非法 `targetRef` 应返回明确错误提示。
- 审批提交时 `expectedVersion` 与当前活动版本不一致，应提示配置已变更，需要刷新后重新提交。
- 提交人审批自己、二级审批人与一级审批人相同、高危活动缺少二级审批等场景应被拒绝并展示原因。
- 模拟运行输入非标准事件、缺少必填字段、幂等键构成字段不足、时间不可解析、`attributes` 类型不合法时，应拒绝模拟并提示字段。
- Fact Query 失败、mapping 失败、字段缺失时，模拟结果必须展示机器原因码，例如 `FACT_QUERY_FAILED`、`FACT_MAPPING_FAILED`、`FACT_FIELD_MISSING`。
- Quota 预览超限时，模拟结果应展示 `QUOTA_EXCEEDED`，且不展示可执行 grant order/outbox 预览。
- 审计数据为空时，展示空态；审计查询失败时，不影响活动详情主体展示。

## 非目标范围

- 不实现外部业务数据库查询，不内置订单、充值、钱包、会员、游戏或风控系统模型。
- 不直接修改用户余额，不绕过 `grant_order` 和 `outbox` 发奖。
- 不新增每个活动的独立业务页面、独立 controller、独立 job 或专属 Kafka topic。
- 不在本需求中交付完整 Admin 鉴权、权限角色体系、生产级菜单权限或公网暴露能力。
- 不在本需求中实现 `MANUAL` / `MANUAL_EXPORT` 完整人工发奖状态机。
- 不在本需求中新增新的 ActivityPlugin 玩法状态表或真实玩法状态消费。
- 不要求后台支持任意脚本规则、外部 SQL、自由公式执行或不受控表达式。
- 不要求本需求解决 Outbox DLQ 重放、发奖回调、对账、超时释放的全部运维后台；这些可作为关联入口或后续需求。

## 风险

- 范围膨胀风险：任务标题是“通用配置页面”，容易扩展成完整营销运营后台。控制口径为先覆盖当前已有 API 和数据模型支持的配置闭环。
- 安全风险：管理后台可修改活动、发奖和预算配置，未鉴权时不能作为公网生产能力。
- 资金风险：奖励、预算、库存、发奖通道配置错误会影响真实发奖。页面必须依赖上线前校验、审批和模拟运行降低风险。
- 规则误配风险：字段路径或类型不匹配可能导致活动误命中或误拒绝。页面必须限制字段路径来源并显示规则解释。
- 多租户风险：入口、人群、审批、审计、回调和 quota 都必须保持 `tenantId` 隔离，页面不得提供跨租户扩大配置的捷径。
- 可用性风险：若只展示原始 JSON，会降低运营可用性；若完全隐藏 JSON，又可能无法覆盖扩展配置。默认口径是表单化核心字段 + 受控 JSON 扩展。

## 验收标准

1. 后台存在统一活动配置入口，可创建和编辑普通配置化活动，覆盖基础信息、时间、入口/展示、人群、规则、奖励、quota、互斥叠加、风控条件和发奖方式。
2. 通过该通用页面至少可以配置一个首存/充值类活动：标准事件为 `DEPOSIT_SUCCESS`，规则使用 `attributes.isFirstDeposit` 和 `attributes.amount`，奖励为 `BONUS RATIO`，发奖通道为 HTTP 或 WEBHOOK。
3. 页面保存的活动配置必须符合现有 API 和数据模型约束，非法状态、非法时间、重复编码、未知配置字段、非法规则字段、非法奖励组合、非法发奖目标都能被阻止并展示原因。
4. 页面支持提交审批、审批通过、审批驳回和审批记录查看；未审批或版本不一致的活动不能从页面上线为 `SCHEDULED` / `ACTIVE`。
5. 页面支持输入标准事件样例进行模拟运行，并展示命中/未命中活动、规则解释、奖励预览、quota 影响和发奖指令预览；模拟运行不产生正式业务副作用。
6. 页面能展示 Quota 不限额、即将超限、已配置预算/库存/次数限制等状态；Quota 超限模拟应展示风险原因且不展示可执行发奖预览。
7. 页面能展示操作审计入口或活动相关审计摘要，覆盖创建、更新、审批、模拟和 quota 创建等关键动作。
8. 验收时不得通过新增某个活动专属页面来满足需求；同一组通用组件应能复用到多种活动类型。
9. 验收文档或测试说明需证明：普通活动新增不需要新增业务专用页面，特殊玩法才考虑 ActivityPlugin。
10. 对当前未实现或不开放能力，例如 `MANUAL_EXPORT`、任意脚本、生产公网无鉴权管理、真实风控判定，页面必须禁用、隐藏或明确提示不可用。
