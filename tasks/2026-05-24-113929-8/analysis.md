## 背景与目标

ExMarketing 是独立活动营销中台，只维护营销系统自己的活动配置、规则、奖励、预算库存、参与记录、幂等和审计，不连接外部业务库、不直接修改用户余额。当前活动状态包含 `DRAFT / SCHEDULED / ACTIVE / PAUSED / ENDED`，活动创建和更新已有基础 Schema 校验、模拟运行、审计和发奖链路。

本需求要补齐“活动配置上线审批流”，目标是：

- 未完成审批的活动不能进入可被事件链路命中的上线状态。
- 已审批但仍处于 `SCHEDULED` 的活动不能被正式事件提前命中。
- 普通活动支持一级审批。
- 高危活动必须二级审批。
- 审批、驳回、上线相关记录可审计、可追溯。
- 提交审批后锁定活动配置版本，避免审批内容与实际上线内容不一致。

## 参与方

- 配置人：创建或修改活动配置，提交审批；不能审批自己提交的审批单。
- 一级审批人：审核普通活动；对高危活动只能完成第一步审批。
- 二级审批人：审核高危活动的第二步；不能与提交人或一级审批人为同一 `operator`。
- 审计/运营排查人员：查询审批记录、驳回原因、版本快照和操作时间线。
- 活动排期/上线链路：只允许已审批通过且版本一致的活动进入 `SCHEDULED` 或 `ACTIVE`。
- 正式事件处理链路：只允许命中已审批通过、版本一致且状态为 `ACTIVE` 的活动；`SCHEDULED` 必须继续按非 ACTIVE 处理，不得被正式事件命中。

最小默认口径：项目当前未定义 Admin 鉴权和角色系统，因此本需求不要求实现权限中心；审批操作必须在请求中显式提供非空 `operator`，并用 `operator` 做“提交人/审批人不能相同”的最小约束。

## 输入输出

### 输入

- 活动 ID：待提交、审批、驳回或查询的活动。
- 操作人 `operator`：提交审批、审批、驳回、撤回等操作必填。
- 操作原因 `reason`：驳回必填；高危二级审批建议必填；普通通过可选但应记录。
- 期望活动版本 `expectedVersion`：提交审批时必填，用于锁定被审批的配置版本。
- 审批动作：提交审批、一级通过、二级通过、驳回、撤回、查询审批记录。

### 输出

- 审批单或审批记录：包含 `tenantId`、`activityId`、`activityCode`、锁定版本、审批状态、风险等级、提交人、审批人、驳回原因、创建/更新时间。
- 活动可排期/上线结果：普通活动一级通过后允许该锁定版本按活动时间进入 `SCHEDULED` 或 `ACTIVE`；高危活动二级通过后才允许进入 `SCHEDULED` 或 `ACTIVE`。
- 事件匹配结果：正式事件只对 `ACTIVE` 活动产生命中；`SCHEDULED` 即使审批通过，也只能作为待生效活动，在正式事件处理时返回或记录非 ACTIVE 拒绝原因。
- 错误输出：对版本不匹配、审批状态不合法、未审批上线、同人审批、高危缺少二级审批、驳回原因缺失等情况返回稳定、可识别的错误原因。
- 审计输出：所有提交、审批、驳回、撤回、上线阻断和上线成功都必须写入审计记录，payload 不包含 secret、token 或完整敏感外部 payload。

## 业务规则

### 活动上线门禁

- 任何活动从 `DRAFT` 或未审批状态进入 `SCHEDULED` / `ACTIVE` 前，必须存在对应活动 ID 和版本的已通过审批记录。
- `PAUSED` 活动恢复为 `SCHEDULED` / `ACTIVE` 时，如果活动配置版本未变化，可沿用原已通过审批；如果配置版本已变化，必须重新提交审批。
- `ENDED` 活动不允许重新审批上线；如需复用，应新建活动或新版本活动。
- 审批通过不等于立即可被事件命中。`APPROVED` 只表示锁定版本通过上线门禁，可进入排期或上线流程；正式事件处理仍必须同时满足 `status=ACTIVE`。
- `SCHEDULED` 活动是待生效/可上线状态，不属于正式事件可命中状态。无论是否已审批通过，正式事件处理不得匹配 `SCHEDULED` 活动；如需要在解释结果中体现，应使用现有非 ACTIVE 拒绝语义，例如 `ACTIVITY_NOT_ACTIVE`。
- 事件处理链路不得命中未审批通过或版本不一致的活动，即使活动 status 被错误设置为 `ACTIVE`，也应被审批门禁阻断。

### 审批状态

最小可验收状态：

```text
NONE
PENDING_L1
PENDING_L2
APPROVED
REJECTED
WITHDRAWN
```

- `NONE`：活动尚未提交审批，默认不能上线。
- `PENDING_L1`：已提交，等待一级审批。
- `PENDING_L2`：高危活动一级通过，等待二级审批。
- `APPROVED`：审批完成，锁定版本允许上线。
- `REJECTED`：被驳回，必须记录驳回原因；配置人修改后需重新提交。
- `WITHDRAWN`：提交人撤回审批；不能上线。

### 普通审批

- 普通活动提交后进入 `PENDING_L1`。
- 一级审批通过后进入 `APPROVED`。
- 一级审批驳回后进入 `REJECTED`，驳回原因必填。
- 提交人不能作为一级审批人。

### 高危二级审批

满足任一条件即按高危处理：

- 奖励类型为资金类 `BONUS` 或 `CASH`。
- 配置了 `BUDGET` 或 `STOCK` quota，或奖励配置会生成外部发奖指令。
- 发奖通道为 `HTTP`、`WEBHOOK` 或 `MQ` 且 `grantMode=AUTO`。
- 规则引用 `facts.*`、`state.quota.*`、`state.plugin.*`，或包含 `RISK` / `LIMIT` 阶段规则。
- 活动配置中包含概率、随机、奖池或分摊类奖励计算方式。

高危活动提交后同样先进入 `PENDING_L1`；一级通过后进入 `PENDING_L2`；二级通过后才进入 `APPROVED`。提交人、一级审批人、二级审批人的 `operator` 必须两两不同。

### 版本锁定

- 提交审批时必须锁定活动当前 `version`，审批记录要保存该版本的活动配置摘要或快照引用。
- 审批过程中活动主配置、规则、奖励、quota 或关键上线字段发生变化时，原审批单不得继续通过上线；最小口径为提交/审批/上线时校验活动当前 `version` 必须等于锁定版本。
- 审批通过只对锁定版本有效；新版本必须重新审批。
- 驳回后修改活动会生成新版本，再提交时应产生新的审批流程或新的审批轮次。
- 已通过审批但仍处于 `SCHEDULED` 的活动，如果在正式生效前修改配置导致版本变化，原审批不得继续用于后续转 `ACTIVE`；必须按新版本重新审批。

### 审批记录与审计

- 审批记录必须能按 `tenantId + activityId` 查询完整时间线。
- 每条审批动作至少记录：动作、操作人、原因、审批前状态、审批后状态、锁定版本、风险等级、发生时间。
- 驳回必须保存明确原因，后续查询能看到最近一次驳回原因和历史驳回原因。
- `marketing_audit` 需要覆盖审批相关动作，便于和已有 `CREATE_ACTIVITY / CREATE_QUOTA / EVENT_IN / QUOTA_EXCEEDED` 审计形成统一排查链路。

## 边界条件

- 活动不存在：返回未找到，不能创建孤立审批单。
- `expectedVersion` 与活动当前版本不一致：拒绝提交或审批，提示版本已变化。
- 已有进行中的审批单时重复提交：不得创建多个并行审批流程；应返回当前审批状态或要求撤回/驳回后重提。
- 已审批通过的同版本重复审批：应幂等返回已通过结果，不重复改变审批状态。
- 驳回原因为空：拒绝驳回。
- 审批人等于提交人，或高危二级审批人与一级审批人相同：拒绝。
- 普通活动被提交为二级审批：允许系统按实际风险等级返回普通审批结果，不强制二级。
- 高危活动只完成一级审批：不能上线，活动仍处于不可上线状态。
- 审批通过后活动时间已过期：审批可记录为通过，但进入 `ACTIVE` / `SCHEDULED` 时仍必须遵守现有时间合法性和状态规则。
- 已审批且处于 `SCHEDULED` 的活动收到正式事件：不得命中，不得发奖，不得扣减 quota，不得创建 participation / grant_order / outbox；应维持现有 `ACTIVITY_NOT_ACTIVE` 拒绝口径。
- 已审批且处于 `ACTIVE` 的活动收到正式事件：还必须继续满足触发事件、时间窗口、入口配置、规则、quota、幂等等既有条件；审批通过不得绕过这些条件。
- 租户隔离：审批查询和动作必须受 `tenantId` 约束，不能跨租户操作活动。

## 异常场景

- 未审批活动直接更新为 `ACTIVE` 或 `SCHEDULED`：必须拒绝，并记录上线阻断审计。
- 已审批但处于 `SCHEDULED` 的活动被正式事件扫描到：必须按非 ACTIVE 拒绝，不得因为审批通过而提前参与事件处理。
- 审批中配置被修改：审批动作或上线动作必须拒绝旧版本，要求重新提交。
- 高危判定失败或未知配置类型：按保守策略视为高危，要求二级审批。
- 审批记录写入失败：审批动作整体失败，不得只更新活动状态。
- 活动上线成功但审计写入失败：按审计强依赖处理，最小口径为拒绝上线或回滚上线动作，避免不可审计上线。
- 并发审批：同一审批单只能有一个最终状态；并发通过/驳回应只有一个成功，其余返回状态冲突或最新状态。

## 非目标范围

- 不实现完整 RBAC、组织架构、审批人分组、站内信或消息通知。
- 不接入外部 OA / Jira / Slack / 企业微信审批。
- 不改变外部事件、Fact Query、Reward Command、Callback 的协议边界。
- 不重构活动规则引擎、奖励计算、quota 扣减、outbox、DLQ 或发奖回调链路。
- 不新增业务专用活动类型或业务系统模型。
- 不处理活动内容编辑器、页面发布、素材审核等营销页面 CMS 流程。
- 不新增自动定时调度器，不改变现有 `DRAFT / SCHEDULED / ACTIVE / PAUSED / ENDED` 状态机含义；本需求只定义审批门禁和审批记录。
- 不要求历史已存在活动自动补审批；历史活动如何治理作为单独迁移任务。

## 风险

- 审批口径与未来 Admin 鉴权不一致：本轮采用 `operator` 最小约束，后续 RBAC 接入时需要映射到真实用户身份。
- 高危判定可能漏判：最小口径采用保守策略，无法识别的发奖或风险配置按高危处理。
- 版本锁定若只校验活动主版本而不覆盖规则/奖励/quota 变更，可能出现审批内容和上线内容不一致；验收时必须覆盖这些配置变化会导致重新审批。
- 审计强依赖会提高上线失败概率，但符合“审批记录可审计”的核心目标。
- 现有 `POST /admin/v1/activities` 示例允许直接创建 `ACTIVE` 活动，本需求落地后该行为需要按审批门禁调整，文档和测试需同步。
- 若实现时把 `APPROVED` 或 `SCHEDULED` 误认为正式事件可命中状态，会提前处理未来排期活动；本需求明确保留现有 `ACTIVE`-only 匹配语义作为架构约束。

## 验收标准

- 创建或更新未审批活动后，尝试让活动进入 `ACTIVE` / `SCHEDULED` 会失败，且返回明确的未审批原因。
- 普通活动提交审批后，一级审批通过即可允许该锁定版本进入排期或上线流程。
- 高危活动提交审批后，一级审批通过仍不能进入排期或上线流程；二级审批通过后才允许进入排期或上线流程。
- 审批通过且状态为 `SCHEDULED` 的活动不会被正式事件命中；事件处理应按现有非 ACTIVE 语义拒绝，不能生成 participation、grant_order、outbox 或 quota 扣减。
- 只有审批通过、版本一致且状态为 `ACTIVE` 的活动，才允许进入正式事件匹配后的规则执行和发奖链路。
- 提交人不能审批自己提交的活动；高危活动的一、二级审批人不能相同。
- 驳回必须填写原因；驳回后活动不能上线；查询审批记录能看到驳回原因。
- 审批提交后修改活动配置会改变版本，旧审批不能继续通过或上线，必须重新提交。
- 审批记录可按活动查询，能展示提交、通过、驳回、撤回、上线阻断和上线成功时间线。
- 所有审批动作和上线门禁结果都有审计记录。
- 事件模拟和正式事件处理均不会命中未审批通过、版本不一致或非 `ACTIVE` 的活动；`SCHEDULED` 在正式事件语义中必须被解释为非 ACTIVE。
- 不影响已审批活动的现有规则执行、奖励计算、quota 原子扣减、grant_order、outbox 和 callback 语义。

## 待确认问题

- 未来是否接入真实 Admin 登录态和 RBAC；本轮默认不接入，用请求 `operator` 做最小身份约束。
- 高危阈值是否需要金额阈值，例如预算超过某金额才二级审批；本轮默认只要资金类、自动发奖、预算/库存/概率/外部事实等风险配置存在即二级审批。
- 历史已存在 `ACTIVE` 活动是否需要强制补审批；本轮默认不迁移历史活动，只约束本需求后续的上线动作和事件命中门禁。

以上问题不阻塞本轮开发，因为已给出保守、最小、可验收默认口径。
