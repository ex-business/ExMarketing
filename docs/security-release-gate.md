# Security Release Gate

This document defines the ExMarketing release security gate. The canonical machine-readable report format is JSON generated by:

```bash
go run ./cmd/security-release-gate \
  --version vYYYY.MM.DD-rc1 \
  --environment production \
  --release-owner release-owner \
  --security-owner security-owner \
  --backend-owner backend-owner \
  --ops-owner ops-owner \
  --config-evidence tasks/<release>/config-evidence.json \
  --risk-acceptance tasks/<release>/risk-acceptance.json \
  --dependency-scan-command "govulncheck ./..." \
  --run-required-commands \
  --output tasks/<release>/security-release-gate-report.json
```

If `govulncheck` or an equivalent dependency scanner is unavailable, omit `--dependency-scan-command`. The report must show that case as WARN for non-production and BLOCK for production unless a valid risk acceptance is supplied.

## Decisions

- `PASS`: all required checks pass, no open P0/P1 security risk exists, and no risk acceptance is needed.
- `WARN`: non-blocking evidence gaps or valid accepted risks exist. Production WARN requires Release Owner and Security Owner confirmation.
- `BLOCK`: any required command fails, any P0/P1 item is open, production baseline evidence is missing, a high-confidence secret is found, or a risk acceptance is invalid.

`BLOCK` always wins over `WARN` and `PASS`.

## Checklist

| ID | Severity | Gate |
| --- | --- | --- |
| Auth | P0 | `EX_MARKETING_REQUIRE_OPENAPI_AUTH=true`, token inventory exists, and token scope is tenant/source constrained. |
| Signature | P0 | Webhook and reward callback tenants use timestamp + HMAC; missing, stale, or invalid signatures do not mutate state. |
| Tenant guard | P0 | Event, callback, Admin, audit, reconciliation, manual grant/export, and DLQ paths cannot cross tenant boundaries. |
| Secret handling | P0 | OpenAPI tokens, webhook/callback secrets, Fact `authRef`, MQ credentials and TLS references stay outside business config, outbox, audit, logs, metrics and reports. |
| Log redaction | P1 | Error responses, provider errors, incident materials and audit summaries redact tokens, headers, secrets and raw payloads. |
| DLQ operations | P1 | Replay/close only applies to `DLQ`; `DLQ_CLOSED` cannot replay; operator and reason are required; customer-visible changes require business confirmation. |
| Export and backup | P1 | Exports/backups record checksum, operator, time, access, retention, encryption/isolation evidence; restore cannot overwrite source or non-drill targets without review. |
| Metrics privacy | P1 | Metrics labels exclude tokens, Authorization, Cookie, secrets, passwords, payloads and high-cardinality business/user identifiers. |
| Threat model | P0 | Every `docs/security-threat-model.md` P0/P1 item is fixed, accepted with valid expiry, or not-applicable with evidence. |
| Alerting | P1 | P0/P1 alert rules and runbooks exist for worker stopped, DB write failure, quota consistency, DLQ growth, outbox backlog and callback failure rate. |

## Config Evidence JSON

```json
{
  "openApiAuthEnabled": true,
  "tokenInventoryEvidence": "vault/exmarketing/openapi-token-inventory",
  "adminProtected": true,
  "metricsProtected": true,
  "factAllowlistNonEmpty": true,
  "callbackSecretsEvidence": "vault/exmarketing/callback-secrets",
  "webhookSecretsEvidence": "vault/exmarketing/webhook-secrets",
  "mqDestinationAllowlist": true,
  "postgreSQLPersistence": true,
  "nonMemoryRepository": true,
  "secretsOutsideBizConfig": true,
  "manualConfirmation": true,
  "releaseWindowEvidence": "change-ticket-123",
  "threatModelStatuses": {
    "TM-01": "fixed"
  },
  "threatModelEvidence": {
    "TM-01": "negative auth tests and production config review"
  },
  "threatModelOwners": {
    "TM-01": "backend-owner"
  }
}
```

Allowed threat model statuses are `fixed`, `accepted`, and `not-applicable`. Every status needs evidence.

## Risk Acceptance JSON

```json
[
  {
    "riskId": "TM-20",
    "severity": "P2",
    "title": "Production restore approval is manual",
    "description": "Restore uses documented two-person review while hard approval integration is pending.",
    "acceptedBy": "security-owner",
    "owner": "ops-owner",
    "reason": "Release is not changing restore behavior and restore is disabled for ordinary production operators.",
    "compensatingControls": "Network isolation, runbook approval, audit evidence and alert review.",
    "expiresAt": "2026-06-30T00:00:00Z",
    "followUpAction": "Add hard approval workflow.",
    "evidence": "change-ticket-123"
  }
]
```

`acceptedBy`, `owner`, `reason`, `compensatingControls`, and future `expiresAt` are mandatory. P0 acceptance also requires `releaseOwnerConfirmed: true` and `securityOwnerConfirmed: true`; otherwise it is invalid and the release remains BLOCK.

## Report Fields

The generated JSON contains `reportId`, `generatedAt`, `version`, `commit`, `environment`, owners, `overallDecision`, `summary`, `checks`, `threatModelItems`, `riskAcceptances`, `openRisks`, `artifacts`, `checklist`, and redacted `sensitiveFindings`.

Reports must not contain raw secrets, full tokens, Authorization or Cookie values, DSN passwords, full provider responses, raw business payloads, or unredacted high-cardinality user identifiers.
