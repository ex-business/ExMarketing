## 背景目标

ExMarketing 是独立活动营销中台，核心链路统一负责活动匹配、规则判断、奖励计算、预算库存、参与记录、幂等、发奖单、Outbox、回调、审计和对账。来源设计文档要求“活动类型插件化”，但插件只负责特殊活动玩法上下文，不负责通用风控、幂等、预算和发奖。

本需求目标是建立 ActivityPlugin 的注册表和生命周期契约，使未来新增玩法型活动时可以通过注册新插件扩展上下文，而无需修改活动主流程。普通满减、首存、续存、签到、任务、VIP、邀请等能通过标准事件、规则、奖励、Quota 表达的活动，仍必须优先走数据配置。

## 参与方

- 活动配置人员：创建活动，可选配置 `pluginCode`，配置规则引用插件上下文字段。
- 外部业务系统：只上报标准事件，不直接调用插件。
- 活动主流程：负责事件接入、幂等、活动匹配、插件上下文装配、规则执行、奖励计算、Quota、participation、grant_order、outbox 和回调。
- ActivityPlugin：只为绑定活动提供特殊上下文、预检查说明和状态变更意图预览。
- 规则与奖励配置：只能通过 `state.plugin.<pluginCode>.*` 读取插件上下文。
- Review/Test/Dev Agent：后续基于本文件审核、设计测试和实现。

## 输入

- 活动配置：
  - `pluginCode` 可选。
  - 未配置 `pluginCode` 时必须走普通配置链路。
  - 配置 `pluginCode` 时必须命中已注册插件，并且插件声明的适用活动类型必须与活动 `activityType` 兼容。
- 标准事件：
  - 仍只允许标准事件字段：`eventId`、`eventType`、`sourceSystem`、`tenantId`、`subject`、`biz`、`occurredAt`、`attributes`。
  - 插件不得要求事件新增非标准顶层字段。
- 插件注册信息：
  - 插件编码。
  - 插件可兼容的活动类型或活动类型集合。
  - 生命周期能力：构建上下文、规则前预检查、资格通过后状态变更意图预览。
- 规则配置：
  - 可引用 `state.plugin.<pluginCode>.<path>`。
  - 不允许使用 `plugin.*`、`state.<activityType>.*` 或短路径别名。

## 输出

- 插件注册表可用于按 `pluginCode` 查找已注册插件。
- 活动创建或上线前校验能识别未知插件和不兼容插件，并给出可审核的拒绝结果。
- 正式事件处理和模拟运行中，绑定插件的活动输出插件摘要：
  - `pluginCode`
  - `pluginContext`
  - `precheckResult`
  - `explain`
  - `stateChangeIntents`
- 插件上下文只通过统一状态路径暴露给规则和奖励：`state.plugin.<pluginCode>.*`。
- 未绑定插件的普通活动不得出现伪造插件上下文，也不得要求插件参与。

## 业务规则

1. 插件适用原则
   - 只有全新玩法上下文无法通过普通活动配置表达时，才新增 ActivityPlugin。
   - 普通首存、续存、满减、签到、任务、VIP、邀请等活动优先使用标准事件、规则、奖励、Quota 和配置 JSON。

2. 插件职责边界
   - 插件可以构建确定性上下文，例如活动系统自身的场次、奖池、抽奖次数、签到连续天数等上下文快照。
   - 插件可以返回预检查结果，用于主流程解释活动是否可继续参与规则判断。
   - 插件可以在资格通过后返回状态变更意图预览，供 snapshot 和模拟运行解释。
   - 插件不得直接发奖、扣预算、扣库存、创建 participation、创建 grant_order、写 outbox、确认 callback、修改外部业务状态或绕过事件幂等。

3. 生命周期默认口径
   - 构建上下文：在规则执行前，为绑定插件的活动生成只读、确定性插件上下文。
   - 规则前预检查：可返回通过、拒绝或错误，并提供机器可识别 reasonCode 和人可读 reason。
   - 资格通过后：只返回状态变更意图预览，不在本阶段执行真实玩法状态写入。
   - 模拟运行与正式处理应使用同一插件生命周期语义；模拟运行必须无副作用。

4. 主流程顺序
   - 标准事件接入和事件幂等仍先于活动处理。
   - 活动匹配仍由通用状态、时间、入口、租户、优先级、互斥和规则体系负责。
   - 插件上下文必须在规则需要读取 `state.plugin.<pluginCode>.*` 前可用。
   - 规则执行顺序仍为 `MATCH -> QUALIFY -> REWARD -> RISK_LIMIT_BUDGET`。
   - 规则通过后的奖励计算、Quota 预留、participation、grant_order、outbox 仍由通用链路负责。

5. 校验规则
   - 活动配置了未知 `pluginCode` 时，创建或上线前校验必须拒绝。
   - 插件已注册但不兼容当前 `activityType` 时，创建或上线前校验必须拒绝。
   - 规则引用 `state.plugin.X.*` 时，活动必须绑定同一 `pluginCode=X`；否则配置校验应拒绝。
   - 绑定插件活动的规则不得引用其他插件上下文。
   - 插件上下文中的金额、概率、库存等仅作为规则/奖励输入或解释，不替代 Decimal 奖励计算和 Quota 原子扣减。

6. 失败处理
   - 插件预检查拒绝时，该活动应表现为规则/活动拒绝，不生成 grant_order/outbox，不扣 Quota。
   - 插件构建上下文失败且该活动依赖插件时，该活动应返回可解释错误，不得默认放行。
   - 插件未注册或不兼容属于配置错误，应在创建或上线前拦截，不能等正式事件运行时才暴露。
   - 未绑定插件的普通活动不受插件注册表影响。

## 边界条件

- 多租户：插件编码是系统能力编码，不得扩大活动自身 `tenantId` 边界；活动仍按租户隔离。
- 幂等：同一标准事件、同一活动的 participation 幂等键规则不变，插件不得加入随机值、当前时间或外部状态破坏幂等。
- 确定性：同一活动配置版本、同一事件、同一活动系统内部状态快照下，插件上下文和预检查结果应可复现。
- 字段路径：插件上下文只允许出现在 `state.plugin.<pluginCode>.*`，不新增标准事件顶层字段。
- 安全：插件不得读取外部业务库、引用外部业务代码包、记录 secret/token/完整 Authorization。
- 模拟运行：插件生命周期参与模拟输出，但不得写 event_inbox、participation、grant_order、outbox、quota 或真实插件状态。
- 兼容性：没有插件配置的历史普通活动应保持原行为。

## 异常场景

- 创建活动时 `pluginCode` 不存在：拒绝，返回配置校验错误。
- 创建活动时 `pluginCode` 与 `activityType` 不兼容：拒绝，返回配置校验错误。
- 规则引用 `state.plugin.RED_ENVELOPE.*`，活动未绑定 `RED_ENVELOPE`：拒绝配置。
- 规则引用 `plugin.RED_ENVELOPE.*` 或 `state.RED_ENVELOPE.*`：拒绝配置。
- 插件构建上下文失败：该活动本次处理结果为 ERROR 或拒绝，保留可解释 reasonCode，不生成发奖链路副作用。
- 插件预检查拒绝：该活动本次不进入可发奖状态，不扣 Quota，不生成 grant_order/outbox。
- 插件返回状态变更意图但后续奖励为 0：只记录 QUALIFIED/零奖励语义，不执行真实状态变更。
- 插件返回状态变更意图但 Quota 不足：Quota 拒绝优先保证无发奖副作用，插件状态变更仍不执行。
- 普通活动未配置 `pluginCode`：插件注册表不可影响活动匹配、规则、奖励、Quota 或发奖。

## 非目标范围

- 不实现具体 `RED_ENVELOPE`、`LOTTERY`、签到、任务、VIP、邀请等玩法插件。
- 不新增插件状态表、奖池表、场次表、排行榜表或抽奖次数真实扣减表。
- 不实现 WebSocket 推送、场次调度、排行榜状态或真实玩法状态提交。
- 不改变标准事件模型，不允许为插件新增事件顶层字段。
- 不改变通用规则引擎、奖励计算器、Quota、participation、grant_order、outbox、callback 的职责边界。
- 不新增业务专用 controller、业务专用发奖逻辑或外部业务库连接。
- 不让插件绕过审批、模拟运行、审计、幂等和租户隔离。

## 风险

- 边界滑坡风险：插件如果承担发奖、预算或幂等，会破坏中台统一账务安全模型。需要在需求和验收中强制禁止。
- 配置误用风险：普通活动过早插件化会导致主流程扩展膨胀。需要要求普通活动优先配置化。
- 路径混乱风险：如果允许多个插件上下文路径，会导致规则配置不可审计。最小口径只允许 `state.plugin.<pluginCode>.*`。
- 确定性风险：插件如果引入随机数、当前时间或外部不可控状态，重复事件和模拟运行结果会不一致。需要要求上下文可复现。
- 审计解释风险：插件拒绝或错误如果没有 reasonCode，会影响运营排障和模拟运行。需要输出插件摘要。

## 验收标准

1. 注册表验收
   - 可以注册一个或多个 ActivityPlugin 能力。
   - 可以按 `pluginCode` 查找插件。
   - 重复插件编码不得产生歧义，应被拒绝或保持明确唯一结果。

2. 活动配置验收
   - 未配置 `pluginCode` 的普通活动仍可按原配置链路创建、模拟和处理。
   - 配置未知 `pluginCode` 的活动会在创建或上线前校验被拒绝。
   - 配置不兼容 `activityType` 的插件会被拒绝。
   - 配置合法插件的活动可以通过校验，并在运行解释中包含插件摘要。

3. 字段路径验收
   - 绑定插件活动允许规则引用 `state.plugin.<pluginCode>.*`。
   - 未绑定插件活动引用 `state.plugin.*` 会被拒绝。
   - 绑定插件活动引用其他插件编码会被拒绝。
   - `plugin.*`、`state.<activityType>.*`、短路径别名会被拒绝。

4. 生命周期验收
   - 绑定插件活动在规则执行前可获得插件上下文。
   - 插件预检查通过时，通用规则、奖励、Quota、发奖链路继续由主流程执行。
   - 插件预检查拒绝时，不生成 grant_order/outbox，不扣 Quota，并输出可解释拒绝原因。
   - 插件构建上下文失败时，不默认放行，并输出可解释错误。
   - 资格通过后的插件状态变更只作为意图预览进入 snapshot/simulate 输出，不执行真实状态写入。

5. 主流程隔离验收
   - 新增一个插件能力不需要修改活动处理主流程的业务分支。
   - 插件不得直接创建 participation、grant_order、outbox 或修改 quota。
   - 重复标准事件不会因插件上下文而重复发奖。
   - 模拟运行无副作用，且输出包含插件上下文、预检查结果和状态变更意图预览。

6. 文档一致性验收
   - README、架构、API 或数据模型文档中对 ActivityPlugin 的职责边界、字段路径和非目标说明保持一致。
   - 明确普通活动优先走数据配置，只有全新玩法才新增插件。
