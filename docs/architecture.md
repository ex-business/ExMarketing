# ExMarketing Architecture

## Goal

`ExMarketing` is a standalone marketing platform that can connect to any business system through events, fact queries and reward commands.

## Core Modules

```text
Event Intake
  -> Idempotency
  -> Campaign Match
  -> Rule Evaluation
  -> Quota / Budget / Inventory
  -> Grant Order
  -> Outbox
  -> External Reward System
```

## API Boundary

External business systems should only integrate through:

```text
Event In        report user/business events
Fact Query      optional external facts
Command Out     reward commands generated by ExMarketing
Callback In     reward delivery result
```

## Current Implementation

The first version is a single Go service with internal module boundaries that mirror the future service split:

```text
internal/httpapi      admin and openapi HTTP boundary
internal/engine       activity match -> rule evaluation -> reward calculation -> grant order -> outbox
internal/marketing    core domain model and repository interface
internal/rule         four-stage rule engine and evaluator registry
internal/reward       fixed and ratio reward calculators
internal/decimal      exact decimal arithmetic for money
internal/worker       outbox sender with retry and DLQ
internal/fact         HTTP fact provider client
internal/plugin       activity plugin registry contract
```

The service supports two repository modes:

```text
default                         in-memory repository
EX_MARKETING_DATABASE_URL set    PostgreSQL repository
```

Local PostgreSQL is provided by `docker-compose.yml` and initializes the first-phase schema from `db/migration/001_marketing_core.sql`.

`db/migration/002_audit_fact_outbox_indexes.sql` adds audit records, fact provider metadata and indexes for quota/outbox processing.

## Implemented Next-Step Capabilities

```text
Quota reservation:
  marketing_quota supports BUDGET, STOCK and USER_LIMIT reservations.
  For rewardable events, participation creation, quota reservation, grant_order
  creation and outbox creation are committed in one activity-level transaction.
  PostgreSQL uses conditional UPDATE statements to avoid read-after-write races.
  STOCK uses ACTIVITY scope with rewardCode as scopeKey; missing quota rows mean
  unlimited quota for backward compatibility.

Outbox sender:
  EX_MARKETING_OUTBOX_WORKER=true enables HTTP/WEBHOOK delivery.
  Failed messages retry with backoff and then move to DLQ.

Simulation:
  POST /admin/v1/simulate evaluates matching activities without writing inbox,
  participation, grant_order, quota, or outbox rows.

Rule execution:
  Rules run in the fixed business order MATCH -> QUALIFY -> REWARD ->
  RISK_LIMIT_BUDGET. The last business stage groups stored RISK and LIMIT
  rule phases; BUDGET remains a quota type, not a rule_phase.
  Each rule returns status, passed, reasonCode, reason, field, expected,
  actual and sort details. Disabled rules are reported as SKIPPED and do not
  affect the decision. New rule types are added by registering an evaluator in
  internal/rule.Registry; the engine service only invokes the staged rule
  executor.

Fact query:
  POST /openapi/v1/facts/query proxies a standard event payload to an HTTP provider.

Audit:
  activity creation, quota creation, event intake and quota rejection are recorded
  in marketing_audit.

Admin page:
  GET /admin/ serves a minimal local admin page for activity list/create and simulation.
```
